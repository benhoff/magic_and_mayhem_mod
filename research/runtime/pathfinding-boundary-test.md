## Inputs and behavior

Four stack DWORDs: X, Y, Z and the existing 22-byte parameter pointer. ECX is
preserved as the receiver for lower support `0x004f4330` and validity `0x004f46b0`
calls. The routine reads mode `+0x0c` (`type_44`) before capturing receiver
`+0x7f0` as boundary B. Modes are dispatched unsigned; values above 3, including
negative DWORDs, return zero. Even invalid modes load B first.

Let H be parameter `+0` (`type_0c`), L be signed DWORD B-H, Z be the requested
layer, and C be parameter `+8` (`object_104`). XY remain unchanged in lower calls.
The result is always integer zero/one:

- Mode 0 returns whether Z < B, with no lower calls.
- Mode 1 first returns one if Z < signed DWORD L+1. Otherwise, Z <= L or Z >= B
  returns zero. Only the remaining interval calls support at the original XYZ.
  Nonzero support returns zero; zero support returns whether C is zero. C is
  read after the support call.
- Mode 2 returns one if Z < L. If Z > L and Z < B, it calls support at XYZ;
  zero support immediately returns one. Otherwise it **rereads H** and computes
  a fresh L from cached B. If Z is not that L, return zero. At exact equality,
  call validity at original XY and signed DWORD Z+1, returning its negation.
  This exact-boundary result does not read C.
- Mode 3 returns zero at Z >= B. Below B, it calls support at XYZ; nonzero
  support returns zero, otherwise the result is whether C is zero, read afterward.

In mode 2, `0x004f42c0` jumps to `0x004f4222`: EAX holds the validity result at
that point, not the capability field loaded on mode 1's earlier path. Preserving
that distinction is necessary for the exact-boundary branch.

The extent, boundary and Z arithmetic preserves signed DWORD wrapping, including
B-H, L+1 and Z+1. Ordinary mode-1 behavior can be described as inclusive below L,
but the assembly's L+1 comparison is retained because overflow changes it.
No local coordinate normalization, global layer clipping, parameter construction,
category store or cell write occurs. Boundary is captured once; mode selection
is not reread after callbacks, but mode 2's extent and modes 1/3's capability are.

## Implementation and wiring

`route_boundary.*` provides `BoundaryHelpers`, `test_boundary` and
`with_boundary_test`. Lower support and validity are explicit callbacks; they can
be supplied by the previously recovered adapters and map data.

Install boundary last among the movement helper adapters, because it captures
the currently installed record and validity callbacks:

```cpp
support = with_cell_support(support, cell_map);
validity = with_cell_validity_test(validity, cell_map);
movement = with_record_query(movement, support);
movement = with_validity_test(movement, validity);
movement = with_boundary_test(movement);
acceptance = with_movement_test(acceptance, movement);
neighbors = with_standard_movement_test(neighbors, movement);
neighbors = with_creature_acceptance(neighbors, acceptance);
```

The adapter replaces only `MovementCheck::check_41a0`, retaining validity and the
two clearance providers. Missing providers throw only when their modeled branch
needs them; these are host setup guards, not engine branches. All callbacks must
represent the same map context. Map/terrain storage remains borrowed with the
lifetime requirements of the cell views. No installed hook or gameplay change is
included. Follow-up: [both clearance predicates](pathfinding-clearance-tests.md) are now
reconstructed; the complete movement-helper native comparison redirects no
instructions.

```bash

```

Validation on 2026-10-02: all twelve CMake suites and ASan/UBSan reconstruction
checks pass. The native comparison passes 50,408 direct predicate cases,
40,960 map-backed cases and 36,864 movement cases: 128,232 total.

Direct cases use an independent ordinary-arithmetic oracle across eight modes,
five boundaries, five extents, fourteen Z values, three capabilities, three
support DWORDs and both validity results. They compare result, exact lower-call
order, coordinate/parameter forwarding and unchanged parameter bytes. Separate
cases cover INT_MIN/MAX wrapping, mode 1's post-query capability read and mode 2's
post-query extent reread. Lower stubs assert receiver preservation using a
context distinct from fixed occupancy context.

Map-backed cases exercise the reconstructed support and validity chains across
all 256 support-placement patterns, four modes, two extents, five layers, both
capabilities and both footprint modes. Movement cases vary vertical transitions,
source overrides, modes, capabilities and footprint size, comparing results and
categories. Cells, terrain records, parameters and receiver bytes are checked
for writes. Remaining clearance callbacks return controlled fixture values.

The optional native driver requires Linux x86 and `g++ -m32`. It hash-checks the
working executable, creates a disposable snapshot and maps it privately. It runs
the compiled test in two separate processes: direct cases keep `0x004f41a0`
original and redirect its two dependencies; integrated cases retain all six
original routines (`0x004f41a0`, `0x004f3320`, `0x004f4330`, `0x004f3440`,
`0x004f46b0`, `0x004f3990`). Only `0x004f44e0` and `0x004f45b0` are redirected
in that integrated run. Prologues are checked before redirects, and fixture
checks return integer EAX values. Original coordinate helpers and the dispatch
table remain intact. No live game is attached or on-disk executable patched;
the source hash is checked after success. All 14 immutable raw decompilation
artifacts and 1,686 instruction-byte chunks pass integrity verification.
